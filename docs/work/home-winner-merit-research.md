# Research: 홈 「후기 많은」 → 지난달 예약 1위 메리트

> 다음: `docs/work/home-winner-merit-plan.md`

## 1. 손님 한 명의 경로

- 시작: 홈에서 터미널·실내/야외·날짜를 고른 뒤 이용 가능 업체 카드를 본다.
- 중간: 카드 이름 아래 칩에 「후기 많은」 또는 「최저가」가 붙는다. 기본 정렬은 「후기 많은 순」.
- 끝: 자세히 / 예약하기.
- 이탈·헷갈림: 와와만 후기가 많아서 「후기 많은」이 사실상 고정 라벨이 된다. 손님이 고른 결과가 아니라 항상 같은 업체로 읽힌다.

## 2. 관련 파일

| 역할 | 경로 |
|------|------|
| 홈 배지·정렬 | `src/pages/HomePage.tsx` (`productBadge`, `mostReviewedId`, `compareHomeCompanies`) |
| 후기 건수 | `src/lib/reviews.ts` → `reviewSummaries` (공개 읽기) |
| 지난달 업체 예약 수 | B2B `functions/src/hqMonthSnapshot.ts` → `companyMonthSnapshots/{id}/months/{YYYY-MM}` |
| 월 스냅샷 권한 | B2B `firestore.rules` (`companyMonthSnapshots`는 본사·해당 업체만, **매출 포함**) |

## 3. 이미 있는 규칙 (코드·합의)

- 홈 카드 배지는 지금 목록의 **이용 가능·비만차** 업체 중에서 하나만. 동점이면 배지 없음. 「후기 많은」이 「최저가」보다 우선.
- 후기 수는 `company.reviews_count`가 아니라 `reviewSummaries` / published 후기.
- 예약 목록을 B2C가 전부 읽어 집계하면 안 된다. `reservations`는 로그인·필드 검증.
- `companyMonthSnapshots`에는 `revenue`가 있다. 손님에게 열면 안 된다.
- 후기 수·예약 건수를 화면에 지어내지 않는다. 와와만 예외 처리하는 하드코딩도 하지 않는다.
- 가짜 「추천순」은 쓰지 않기로 했다.
- Functions·rules 배포는 B2B만.

## 4. 건드리면 안 되는 것

- [x] Functions / Firestore rules 배포는 B2B(`airpick2-b-to-b`)만
- [x] 후기 수·보험 보장·복귀 시간 등 숫자 지어내기 금지
- [x] 비회원 예약을 카카오 계정에 자동 병합 금지 (합의 전까지)
- [x] main만 사용. cursor/* 브랜치 만들지 않음
- [x] 커밋·푸시·호스팅 배포는 요청 전까지 금지
- 기타: 월 스냅샷 매출·건수를 손님 클라이언트에 열지 않음. 입점 수수료·정산 할인 같은 업체 정산 메리트는 이번 범위 아님.

## 5. 모르는 것 / 확인 필요

- 지난달 1위 기준을 `admitted`(그달 입고 예정)로 할지 `reserved`(그달 접수)로 할지. 스냅샷에 둘 다 있음. **입고 예정(admitted)** 이 「실제로 맡긴 건」에 가깝다.
- 이번 달 1일~스냅샷 생성 전까지는 지난달 문서가 없을 수 있음. 그때 후기 폴백을 쓸지, 배지를 숨길지.
- 목록이 터미널·실내/야외로 갈리는데 월 스냅샷은 업체 전체 건수다. 목록에 있는 업체끼리만 비교하면 된다 (조건별 건수는 없음).

## 6. 한 줄 결론

이 작업의 범위는 **누적 「후기 많은」 칩을 없애고, 지난달 예약(입고) 1위 업체에게 홈 노출 메리트(칩+기본 정렬 맨 위)를 주는 것** 이고, 하지 않는 것은 **와와 하드코딩, 예약 건수 표시, 월 스냅샷 공개, 정산 할인, 가짜 추천순** 이다.
